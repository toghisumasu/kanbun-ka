# Jev エコシステム観察メモ
**2026年9月19〜20日 週末2日間の動向整理**

---

## 1. Jevとは何か

TypeSafe AIが開発した「**判断特化型AIモデル**」。

通常のLLM（Claude・GPT・Gemini）はテキストや構造化データを**生成**する。
Jevはそれをしない。与えられた入力に対して「**命題が成り立つか**」を確率スコアで返すだけ。

```
通常のLLM: プロンプト → [推論] → テキスト生成（数百ms〜数秒）
Jev:       入力 + 命題 → [判断] → 確率スコア（40〜200ms）
```

### 核心的な3行

> LLMは推論し生成する。  
> Jevは評価し決定する。  
> ソフトウェアは実行する。

---

## 2. ベクトル検索との違い

意味的な近さを測る「ベクトル検索」とも異なる。

| | ベクトル検索 | Jev |
|--|--|--|
| 問い | 「話題が近いか」 | 「命題が成り立つか」 |
| 「返金してほしい」vs「返金完了」 | ほぼ同距離（意味が近い） | 0.98 vs 0.10（意図が違う） |
| 否定検索 | 苦手 | `-v` でそのまま動く |
| AND/OR | 困難 | ブール演算として機能 |

---

## 3. 確率がキャリブレーションされている

Jevの最大の特徴は「**確率の意味が保証されている**」点。

- スコア0.98 → 「ほぼ確実に成り立つ」
- スコア0.10 → 「ほぼ成り立たない」
- この数値が閾値として実際に機能する（`--level loose/strict`で調整可能）

通常のLLMが返すconfidenceは校正されておらず、意思決定には使いにくい。

## 4. アーキテクチャの位置づけ

```
┌─────────────────────────────────────────┐
│  System Two（遅い・深い・生成）          │
│  LLM: Claude / GPT / Gemini / ローカル  │
│  役割: 推論・計画・テキスト生成          │
└──────────────────┬──────────────────────┘
                   │
┌──────────────────▼──────────────────────┐
│  判断レイヤー（速い・安価・評価）         │
│  Jev / jev互換モデル                    │
│  役割: 評価・分類・ルーティング・検証     │
└──────────────────┬──────────────────────┘
                   │
┌──────────────────▼──────────────────────┐
│  ソフトウェア（実行）                    │
│  既存システム・エージェントハーネス       │
└─────────────────────────────────────────┘
```

「置き換えではなく、既存システムの周囲に高速意思決定レイヤーを追加する」

### 5-4. verifier（生成物の達成確認）

```
エージェントの1ターン完了
        ↓
Jev: 「ゴールは本当に達成されたか？」→ YES/NO
        ↓
NO → 継続  /  YES → 次へ
```

従来：高価な推論モデルで検証 → コストが高く頻度を下げざるを得ない  
Jev：安価・高速 → **毎ターン後に必ず確認**できる

| 事例 | 内容 |
|------|------|
| **devagrawal09/jev-review** ★250 | Git diffを正しさ/安全性/互換性/テストリスクで評価 |
| Magic Jev Ball | GitHub PRのCI・diff・レビューを確認して「承認すべきか」を判定 |
| /goal verifier | エージェントハーネスの目標達成確認に差し込む |

## 7. waka-collector への示唆

### 現行アーキテクチャとの対応

```
A層: ShikimokuChecker（純Ruby・決定論的式目判定）
B層: BuiDictionary・MeCab（辞書・フィルタリング）
C層: qwen3:14b メンタムさん（創造的付句生成）
```

Jevの位置：**B層とC層の間**、および**C層の出力後**

### 具体的な適用候補

#### 候補1★★★: Stage 1.5（bui宣言の距離適合チェック）
設計済み2段階方式に差し込む：

```
Stage 1: メンタムさんがbuiをJSON宣言
              ↓
【新】Stage 1.5: 宣言buiが折別目標距離を満たすか？
      → GO / TOO_NEAR / TOO_FAR（高速判断）
              ↓ GO
Stage 2: 承認されたbuiで付句を詠む
```

距離評価関数（Phase0〜1.5完了済み）の設計思想と直結。

#### 候補2★★: 恋句の文脈判定（B層補完）

BuiDictionaryの構造的限界（語彙のみ・文脈依存60〜70%未達）を補完：

```
入力: 前句 + 付句候補 + 前後2〜3句
出力: 恋(0.95) / 非恋(0.08) → 閾値で判断
```

ShikimokuCheckerへの配線も自然。

#### 候補3★: Step 1.5 condense/expand方向判断
モーラ超過・不足時の修正方向をLLM説明文でなく **CONDENSE/EXPANDの1値** で返す。  
（Ruby側でdelta計算できるなら不要）

### ローカル実現の道筋

```
現状:
  Ollama（llama.cppベース）→ メンタムさん(14b)

llama.cppにjev互換が入れば:
  軽量判断モデル(0.8b〜2b) → 式目verifier・bui判定・距離チェック
  メンタムさん(14b)         → 付句生成のみ集中
```

Mac mini M4の余剰メモリなら0.8b〜2bは実質コストゼロで同居可能。
